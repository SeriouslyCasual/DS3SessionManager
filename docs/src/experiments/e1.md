# E1: Observability map

**Question.** What can a third-party tool observe about Dark Souls III peer-to-peer (P2P) sessions, and how reliably?

**Status.** Run complete on a two-PC local network (LAN), in both direct and relayed sessions. The outcomes below update the original hypotheses.

## Hypotheses and outcomes

| | Hypothesis | Outcome |
|---|---|---|
| H1 | A second process initialised with AppID 374320 sees the game's sessions through `GetP2PSessionState`. This is undocumented by Valve but used by DS3ConnectionInfo. | **Confirmed.** Peer Steam ID, name, state and relay flag are all visible. |
| H2 | Steam reports `m_nRemoteIP` as a host-order integer, so `Ipv4Addr::from(u32)` gives the correct address. | **Confirmed** for direct sessions. Kernel Event Tracing for Windows (ETW) reports addresses and ports in the opposite byte order; ds3sm calibrates this automatically. |
| H3 | Steam's connectivity checks show up as 56-byte requests and 68-byte replies in kernel ETW. | **Confirmed**, with one correction: the packets belong to **steam.exe**, not `DarkSoulsIII.exe`. Steam sends one check about every 500 ms per peer, on direct and relayed paths alike. E2 confirmed the size rule against packet captures. |
| H4 | Most sessions are direct (not relayed) unless a player sets Steam's IP-sharing option to restrict sharing. | **Partly rejected.** On a LAN, setting the option to *Never* on both PCs (with Steam restarted) still gave a direct session. A firewall block did force a relay. |

Additional findings:
- **The game's P2P traffic, including the connectivity checks, is sent and received by the Steam client (steam.exe).** A tool that watches only the game process sees no peer traffic.
- **For a relayed session, Steam's report is incomplete and comes in two forms.** In the E1 run, Steam set its relay flag and reported the peer's own public address, to which no packets go. The traffic went to a Valve relay server that Steam does not name. Later runs (E2) also showed the opposite form. The relay flag was off, and a relay endpoint was reported as if it were the peer; the peer's traffic arrived from a second relay endpoint. Steam's flag alone is therefore not a reliable relay indicator. ds3sm combines it with three other signals and infers the relay endpoints from steam.exe's traffic, marking the result `yes*` (see E2).
- **The 56/68-byte checks still run through the relay.** The resulting round-trip time (RTT) was about twice the RTT to the relay's network. This indicates an end-to-end measurement (player to relay to player and back), not just a measurement to the relay.

## Setup

- **PC-A** (main) runs `ds3sm`, elevated.
- **PC-B** is a second PC with its own Steam account. Note its public IP and LAN IP beforehand, from the router or `curl ifconfig.me`.
- Same patch level on both; record the game version from the title screen.
- Download the DB-IP City Lite database and save it as exactly `geo/dbip-city-lite.mmdb`. Optionally, also save the DB-IP autonomous system number (ASN) Lite database as `geo/dbip-asn-lite.mmdb` (one of the relay signals).

## Procedure

1. **PC-A, before playing:**
   1. Start Steam.
   2. Start DS3 and load a character.
   3. In an elevated terminal, run `ds3sm probe`. Record the output.
2. **PC-A:** start the monitor:
   `ds3sm monitor --label "E1 A<->B direct" --home-lat <lat> --home-lon <lon>`
3. **Co-op:**
   1. PC-B places a summon sign (white soapstone) near a bonfire both players can reach.
   2. PC-A summons PC-B.
   3. Play for 5 minutes.
   4. Dismiss the phantom.
4. **Checks:**
   - [ ] PC-B's Steam ID appears in the table (H1).
   - [ ] The remote IP equals PC-B's public IP, or its LAN IP if both PCs are on the same LAN (H2).
   - [ ] The RTT and packets-per-second columns fill in (H3). While PC-B is summoned, `ds3sm probe` also lists which process exchanges packets with the peer.
   - [ ] Relay shows `no` (H4).
5. **Relay condition.** The IP-sharing option alone does not force a relay between PCs on the same LAN. Use a firewall block instead:
   1. Dismiss PC-B, so no session is active.
   2. On PC-A, in an elevated PowerShell, block UDP to and from PC-B's LAN address:
      `New-NetFirewallRule -DisplayName "ds3sm E1 block direct" -Direction Outbound -Protocol UDP -RemoteAddress <PC-B LAN IP> -Action Block`
      `New-NetFirewallRule -DisplayName "ds3sm E1 block direct in" -Direction Inbound -Protocol UDP -RemoteAddress <PC-B LAN IP> -Action Block`
   3. Summon PC-B again and repeat steps 2–4. (The rules can also go on PC-B instead, blocking PC-A's LAN address.)
   4. Expect relay `yes*`, with a Valve relay endpoint as the remote, the `via` column showing which relay signals fired, and the RTT and packets-per-second columns filled in. `ds3sm probe` shows Steam's reported remote: either PC-B's **public** IP with Steam's relay flag on, or a relay endpoint with the flag off. Reconnecting (quitting to the title screen and summoning again) can switch between the two.
   5. Remove the rules afterwards:
      `Remove-NetFirewallRule -DisplayName "ds3sm E1 block direct","ds3sm E1 block direct in"`
   6. Optional: to test whether the IP-sharing option forces a relay between different networks, put PC-B on another network (e.g., a phone hotspot) with the option set to *Never* on both PCs.
6. **Public sessions:**
   1. Leave the monitor running during ordinary online play (summoning strangers, being invaded) for at least 30 minutes.
   2. Count sessions: direct vs. relayed, with and without an inferred relay endpoint.
7. **Export each run:**
   `ds3sm export --db runs/<file>.sqlite --out <export-folder>/E1/<run> --salt <secret>`

## Same-LAN caveat

When PC-A and PC-B share a LAN, Steam connects them over LAN addresses, and the direct RTT is under 1 ms. That still tests H1–H3. Geographic questions need players on other networks (E5).

## Record

Keep run notes alongside each export, with:
- game version, Steam client version, Windows build;
- every checklist answer;
- the exact wording of any Steam setting changed;
- anything unexpected.
