# E2: Measurement validation (ETW RTT vs. packet capture)

**Question.** How accurate is round-trip time (RTT) derived from kernel Event Tracing for Windows (ETW), and how reliable is identifying Steam's connectivity checks by packet size alone?

**Status.** Complete for one direct and two relayed sessions on a two-PC local network (LAN), each captured for about 10 minutes. The outcomes are below; the original protocol follows.

## Outcomes

### Steam's checks use classic STUN

Steam's connectivity checks are **classic RFC 3489 Session Traversal Utilities for NAT (STUN)**, not RFC 8489: there is no magic cookie, and the transaction ID is 128 bits. A request (type `0x0001`) carries one USERNAME attribute and is 56 bytes; a response (`0x0101`) adds a MAPPED-ADDRESS attribute and is 68 bytes. The planned fallback was not needed, because the transaction ID still pairs each request with its response exactly. Checks run in both directions, one about every 500 ms per side.

### Accuracy

I captured on PC-A with Npcap while `ds3sm monitor` ran, then compared the two with `analysis/e2_validate.py`. Table I summarises the three captures.

**TABLE I.** ETW-based measurement compared with packet capture

| | Direct (LAN) | Relayed, mode A | Relayed, mode B |
|---|---|---|---|
| Size rule precision and recall, requests | 1.0000 / 1.0000 | 1.0000 / 1.0000 | 1.0000 / 1.0000 |
| Size rule precision and recall, replies | 1.0000 / 1.0000 | 1.0000 / 1.0000 | 1.0000 / 1.0000 |
| ETW samples matched to capture pairs | 1133 / 1133 | 1340 / 1340 | 996 / 996 |
| RTT difference, ETW minus capture: median | +0.029 ms | +0.032 ms | +0.036 ms |
| RTT difference: p95 / max | +0.039 / +0.063 ms | +0.042 / +0.118 ms | +0.049 / +0.081 ms |
| RTT (capture): median | 0.30 ms | 23.4 ms | 22.3 ms |

Modes A and B are the two ways Steam reports a relayed session (see below). In all three captures:
- The 56/68-byte rule found every check and nothing else: no false positives, no missed STUN sizes.
- ETW always read slightly **high**, by about 0.03 ms and never below the capture. ETW timestamps packets at the transport layer and Npcap at the network-driver layer, so ETW's RTT includes PC-A's own network stack in both directions. That is about 10% of a LAN RTT and about 0.1% of a relayed one.
- The two clocks agreed to within microseconds (offset under 0.02 ms, no measurable drift).
- PC-A's own Steam client answered the other side's checks in about 0.06 ms (median). On the LAN, 22% of RTT samples were above 1 ms while PC-A's turnaround never was, so those spikes come from the other PC or its link.

### Pairing under loss

Without transaction IDs, each reply has to be paired with a request by timing. The original rule paired it with the **oldest** unanswered request. A single lost reply then shifted every later pair by one check (about 500 ms) for the rest of the session. A relayed 22 ms RTT read as about 515 ms, because the stale request never reached the 2 s timeout. ds3sm now pairs each reply with the **newest** request sent before it, and counts older unanswered requests as lost. The mode B capture had three lost replies: the newest-request rule paired 1349 of 1349 replies correctly, while the old rule would have paired 18 (1.3%). The new rule assumes the RTT is shorter than the check interval (about 500 ms).

### Relayed sessions

Steam reported the two relayed sessions in two different ways:
- **Mode A:** Steam's relay flag is **off**, and the reported remote address is a Valve relay endpoint. PC-A sends to that endpoint and receives only the STUN replies from it. The other player's traffic arrives from a second relay endpoint, sometimes on another relay host, wrapped in a relay header of 44 bytes (64 bytes on packets sent that way). The header is a relay message older than Traversal Using Relays around NAT (TURN), in the style of RFC 3489 (a data indication or send request carrying the original packet). Most likely, each player has a relay allocation, and PC-A sends straight to the other player's.
- **Mode B:** Steam's relay flag is **on**, and the reported address is the other player's public IP, to which no packets go. One relay endpoint carries all traffic in both directions, unwrapped.

The same settings gave either mode. The mode changed after reconnecting, not with Steam's IP-sharing setting or with which PC was firewalled. In both modes the 56/68-byte checks run through the relay, and the RTT is end to end (player to relay to player). Relaying added **no packets**: outbound rates were 37.2 (direct), 35.5 (mode A) and 37.6 packets/s (mode B), with matching per-size rates.

These findings led to two changes in ds3sm:
- **Relay detection.** Steam's flag alone is unreliable, so ds3sm now combines four signals: Steam's flag, a traffic-asymmetry pattern, an optional network-ownership (ASN) lookup, and a built-in list of Valve's address space and Steam relay sites.
- **Relay attribution.** Every relay endpoint is now counted for the relayed player, so inbound rates are correct in both modes.

## Ground truth

Npcap on PC-A captures the same traffic as ETW, with payloads. In the capture:
- STUN messages are identified by their header: the RFC 8489 magic cookie `0x2112A442`, or a strict classic RFC 3489 check (exact length field and attributes that fill the message);
- requests and responses are paired by **transaction ID**.

That pairs each request with its response exactly.

## Procedure

1. Install Wireshark with Npcap. Find PC-A's network adapter number with `dumpcap -D`.
2. On PC-A, start a capture (11 minutes):
   `dumpcap -i <adapter> -f "udp and host <PC-B IP>" -a duration:660 -w runs\e2_direct_1.pcapng`.
   For a relayed run, use the filter `udp`, because the relay address is not known in advance.
3. At the same time, run `ds3sm monitor --label "E2 run N"`, and stop it before the capture ends.
4. Keep a co-op session with PC-B going for about 10 minutes.
5. For a relayed run, block UDP between the two PCs with Windows Firewall rules (on either PC) before summoning, as in E1.
6. Run the analysis on the capture and the matching run database:
   `python -I analysis/e2_validate.py runs/<capture>.pcapng runs/<run>.sqlite --json runs/<capture>.json`.
   It:
   - parses STUN in the capture and pairs it by transaction ID;
   - matches the pairs to ETW samples by reply time;
   - reports:
     - the RTT error distribution (ETW minus capture): median, p95, max;
     - **precision and recall** of "56-byte send = STUN request" and "68-byte receive = STUN reply";
     - how often size-only pairing picks the wrong request, under both the newest-request and oldest-request rules;
     - the timestamp resolution of each source;
     - packets per second by size, and, for relayed runs, the relay endpoints' traffic with relay headers removed.

## Note on clocks

ETW uses kernel timestamps at QueryPerformanceCounter (QPC) precision; Npcap uses its own timestamps. Both are on the same host, so an offset between them does not matter. Only RTT differences are compared, and the script estimates and reports the offset and drift anyway.
