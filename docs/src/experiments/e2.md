# E2: Measurement validation (ETW RTT vs. packet capture)

**Question.** How accurate is ETW-derived RTT, and how good is the size-only STUN heuristic?

## Ground truth

**Wireshark/Npcap** on PC-A captures the same traffic as ETW, with payloads. In the capture:
- STUN messages are identified by the RFC 8489 header: magic cookie `0x2112A442` at payload offset 4, with method and class in the first 2 bytes;
- requests and responses are paired by their **96-bit transaction ID**.

That gives exact request/response pairs.

> **Open:** Steam may wrap or encrypt its connectivity checks, so the RFC header might not appear. If so, the analysis falls back to pairing by size plus timing, and compares against the injected-delay ground truth (E3) instead. Either outcome is reported.

## Procedure

1. Install Wireshark with Npcap.
2. On PC-A, start a capture filtered to the peer: `udp and host <PC-B IP>`.
3. At the same time, run `ds3sm monitor --label "E2 run N"`.
4. Keep a co-op session with PC-B going for 10 minutes. Repeat 3 runs.
5. Export the capture: `tshark -r cap.pcapng -T fields -e frame.time_epoch -e ip.src -e ip.dst -e udp.length -e data.data > cap.tsv`.
6. Run `analysis/e2_validate.py` (to be written). It:
   - parses STUN in the capture;
   - builds ground-truth RTT pairs;
   - matches them to ETW samples by time;
   - reports:
     - the RTT error distribution (ETW minus pcap): median, p95, max;
     - **precision and recall** of "56-byte send = STUN request" and "68-byte receive = STUN reply";
     - how often the size-only pairing would pick the wrong request under loss;
     - the timestamp resolution observed in each source.

## Note on clocks

ETW uses QPC-precision kernel timestamps. Npcap uses its own timestamps. Both are on the same host, so an offset between them doesn't matter; only RTT differences are compared.
