# E3: Injected delay and loss

**Question.** Does the round-trip time (RTT), loss and jitter that ds3sm measures track delay and loss injected on purpose? At what point does Dark Souls III drop a session, and what does the tool show before it?

**Status.** Complete on a two-PC local network (LAN). The outcomes are below; the protocol follows.

## Outcomes

### Delay

I added delay on PC-A with clumsy 0.3, which uses the WinDivert packet filter, in both directions or in one. Event Tracing for Windows (ETW) timestamps packets above the filter and the packet capture below it, so the capture never sees the injected delay. The difference between the two RTTs is therefore the delay clumsy actually applied. Table I shows the results (each condition about 2 minutes).

**TABLE I.** RTT and jitter under injected delay

| Condition | Added RTT (ETW − capture) | Nominal | `jit` (ms) | Jitter below the filter (ms) |
|---|---|---|---|---|
| No delay | 0.0 ms | 0 | 0.64 | 0.60 |
| 10 ms each way | 45.0 ms | 20 | 8.42 | 0.44 |
| 25 ms each way | 75.9 ms | 50 | 6.92 | 0.68 |
| 50 ms each way | 123.0 ms | 100 | 7.87 | 0.69 |
| 100 ms each way | 222.2 ms | 200 | 7.13 | 0.82 |
| 200 ms each way | 416.0 ms | 400 | 8.33 | 0.78 |
| 50 ms outbound only | 61.5 ms | 50 | 0.55 | 0.54 |
| 50 ms inbound only | 60.0 ms | 50 | 6.73 | 0.53 |

- ds3sm's RTT rose with the injected delay at a slope of about 1. clumsy added about 10–12 ms more per delayed direction than its setting, and that extra varied by up to about 30 ms. The ground truth is therefore the measured difference, not clumsy's setting.
- Each one-way condition added half of the two-way one, as the layering predicts.
- clumsy's delay is not constant: with inbound delay active, `jit` rose to 7–8 ms while the same estimator below the filter stayed under 1 ms. ds3sm measures the jitter where the game receives the packets.

### Loss

Table II compares ds3sm's `nrep%` (the share of Steam's checks without a reply) with the loss measured from the capture in each direction.

**TABLE II.** Check loss under injected loss

| Condition | `nrep%` (95% confidence interval) | Outbound loss | Inbound loss | 1 − (1 − out)(1 − in) |
|---|---|---|---|---|
| 1% each way | 2.1 (1.0–4.6) | 1.1% | 1.1% | 2.1% |
| 5% each way | 13.8 (10.5–17.9) | 7.2% | 7.1% | 13.8% |
| 10% each way | 21.8 (17.4–26.8) | 12.9% | 10.2% | 21.8% |
| 20% each way | 46.6 (41.1–52.3) | 27.2% | 26.7% | 46.6% |
| 10% outbound only | 12.8 (9.4–17.3) | 13.2% | 0% | 13.2% |
| 10% inbound only | 12.5 (9.2–16.9) | 0% | 12.2% | 12.5% |

- `nrep%` matched the loss actually applied in every condition, and loss appeared only in the direction it was injected.
- clumsy dropped more than its setting at 5–20%, so `nrep%` sits above 1 − (1 − p)² for the nominal p.
- `jit` stayed at 0.2–0.3 ms under loss: the estimator absorbs a missing packet instead of counting it as jitter.

### Two limits found

**RTT above the check interval.** Steam sends a check about every 487 ms. When the true RTT is longer than that, each reply arrives after the next check has gone out. Pairing a reply with the newest check sent before it then reads the RTT modulo 487 ms, and nothing flags it (Table III).

**TABLE III.** RTT read by ds3sm when the true RTT exceeds the check interval

| Delay each way | True RTT (approx.) | ds3sm median | Predicted (true mod 487 ms) |
|---|---|---|---|
| 250 ms | 522 ms | 36.7 ms | 35 ms |
| 500 ms | 1022 ms | 49.3 ms | 48 ms |
| 1000 ms | 2022 ms | 69.9 ms | 75 ms |
| 2000 ms | 4022 ms | 121.5 ms | 127 ms |

ETW does not expose the packet contents, so the transaction IDs that would resolve this are not available. ds3sm's RTT is therefore valid below about 460 ms. That limit is far outside playable conditions.

**Jitter under heavy loss.** At about 50% inbound loss, most gaps between surviving packets span two or more send slots. The period estimate (the median gap) then doubled, and `jit` read 45–65 ms on a clean stream. ds3sm now measures each gap per slot, and starts a new stream's period from a low percentile of its first 16 gaps. Replayed on the captured stream with the measured loss applied, the old rule read a median of 47.4 ms and the new one 0.25 ms. A new stream starting under 60% loss learned the right period in 5 of 200 random trials with the old rule and in 199 of 200 with the new one.

### Where the session breaks: Steam fails over first

Dark Souls III never dropped the peer-to-peer (P2P) session. Steam moved it to another path first:
- **With only the direct path impaired:**
  - At 50% loss each way, Steam renegotiated the connection repeatedly but stayed direct. The game was already unplayable: characters slid instead of walking, and no hits registered.
  - At 75% loss, Steam moved to a relay within 16 s. The first relay it chose was a distant site at 307 ms RTT, between two PCs on the same LAN.
  - At a 10 s RTT, Steam moved to a relay within 8 s, this time the nearest site (22 ms).
- **With all UDP impaired:** Steam moved the session to **a direct TCP connection** between the two Steam clients. It carries the same datagrams, each with a 2-byte length prefix. Steam's status interface still reported a direct UDP session, so a UDP-only tool loses it.
- **What did cause a disconnect:** the game's link to its own servers. It has no such fallback, and at 90% loss the game returned to the title screen with a lost-connection message. Under a 10 s RTT, that link survived.
- **Leaving TCP:** once on TCP, Steam stayed there while TCP worked, even after UDP had recovered. It returned to UDP about 4 s after TCP itself became bad.

### Measuring over the TCP fallback

ds3sm now follows the TCP fallback, unless it is started with `--no-tcp`. I checked it against the capture by reassembling the TCP stream and reading the transaction IDs inside the frames:
- **Receive events** come one per TCP segment, timestamped within 0.02 ms of the capture. ds3sm's jitter on the TCP path matched the capture's to within 0.001 ms. It was 4.2–4.5 ms on the LAN, against about 0.35 ms on UDP.
- **Send events** come one per message, but are timestamped when the data is acknowledged, so a check cannot be timed against its reply. RTT on TCP therefore comes from Windows' own TCP statistics for the connection, as the 10 s minimum of its samples. The minimum removes the waits for delayed acknowledgements, which pushed the average to about 30 ms on the LAN. Table IV compares it with the true network RTT.

**TABLE IV.** RTT on the TCP fallback

| Condition | Network RTT (truth) | ds3sm | Game-message RTT (truth) |
|---|---|---|---|
| LAN | 0.04 ms | 0 ms (1 ms resolution) | 0.3 ms |
| TCP delayed 50 ms each way | ≈161 ms | 160 ms | 325 ms |
| TCP delayed 100 ms each way | ≈243 ms | 241 ms | 365 ms |

The truth comes from the measured injected delay: ETW sees each received segment after the filter, the capture before it.

On TCP, the game's messages took about twice the network RTT under delay. Movement looked choppy at 50 ms of TCP delay, while UDP with 250 ms each way stayed smooth.

### Why delay makes movement choppy on TCP but not on UDP

The other player's game sends a position update about every 83 ms (12 Hz). Table V shows how those updates arrived at PC-A on each path. A gap under 10 ms means two updates arrived practically together.

**TABLE V.** Arrival of the other player's 12 Hz updates

| Path and delay | Gap between updates: median | p95 | Max | Gaps under 10 ms |
|---|---|---|---|---|
| UDP, no delay | 83.3 ms | 83.8 ms | 89 ms | 0–2% |
| UDP, 250 ms each way | 83.3 ms | 83.8 ms | 242 ms | 0% |
| TCP, no delay | 83.3 ms | 88.6–100 ms | 242 ms | 1–2% |
| TCP, 50 ms each way | 81.6 ms | 167.9 ms | 246 ms | 48% |
| TCP, 100 ms each way | 120.6 ms | 126.7 ms | 1248 ms | 37% |

**On UDP,** every update travels as its own packet, independently of the others:
- A constant delay shifts all updates by the same amount, so they still arrive one every 83 ms, only later. The game smooths that steady stream, so movement looks delayed but fluid.
- A lost update is simply skipped, and the next one is not held back.

**On TCP,** the updates are carried as one ordered, reliable byte stream:
- **Updates bunch at the round-trip pace.** With 50 ms each way, about half of the updates arrived together with another, and the next pair came about 168 ms later. That is two updates per round trip (about 161 ms) instead of one every 83 ms. With 100 ms each way, the gaps stretched to 120 ms and occasionally to over a second. This is the behaviour of TCP sending a small message only once the previous one has been acknowledged (Nagle's algorithm). Whenever the round trip exceeds the 83 ms update interval, new updates wait for a full round trip. The game's own check replies were held back in the same way (the doubled message delay in Table IV).
- **Everything waits for anything delayed or lost.** TCP delivers in order, so one late or resent segment holds back every update behind it. This is head-of-line blocking.
- **The result is choppy movement.** The game receives two or three positions at once, then nothing for one or two update intervals. The other player appears to jump instead of moving smoothly, which matches the choppy movement observed. ds3sm's `jit` shows this: 2.6 ms at 50 ms and 21.9 ms at 100 ms of TCP delay, measured on the arrival times of the updates, against 0.2–0.3 ms on UDP.

TCP's reliability, which helps most traffic, works against a real-time game here. Late information is held back until it is useless, instead of being skipped. On the TCP fallback, the ping therefore understates how bad the connection feels; jitter and the bunching of updates show it.

## Ground truth

- **Delay:** ETW timestamps at the transport layer, WinDivert works at the network layer, and Npcap captures at the adapter. ETW − capture RTT is the injected round-trip delay. The ETW receive time of a segment minus its capture time is the injected inbound delay.
- **Loss:** checks seen by ETW but not by the capture were dropped outbound. Replies seen by the capture but not by ds3sm were dropped inbound.
- **TCP:** Steam's frames are reassembled from the capture, and checks are paired by transaction ID, as in E2.

## Procedure

1. On PC-A, run clumsy 0.3 as administrator. The filter is `udp and (ip.SrcAddr == <PC-B> or ip.DstAddr == <PC-B>)`. For the TCP and all-UDP runs, use `udp and udp.DstPort != 53 and udp.SrcPort != 53` (keeping Domain Name System (DNS) lookups working), then `tcp and (ip.SrcAddr == <PC-B> or ip.DstAddr == <PC-B>)`.
2. Run a capture (`dumpcap -i <adapter> -f "udp"`, or `host <PC-B>`) and `ds3sm monitor` at the same time. Record each change with a timestamped mark (`<ISO time> <label>`).
3. Run the blocks:
   - **A, delay:** 10, 25, 50, 100 and 200 ms each way, then 50 ms one way each, 2 min each.
   - **B, loss:** 1, 5, 10 and 20% each way, then 10% one way each, 2 min each.
   - **C, drop point:** loss 50–100% and delay 250–5000 ms each way, 1 min each or until the session changes.
   - **TCP runs:** fall back with all-UDP impairment, then delay only the TCP connection.
4. Analyse: `python -I analysis/e3_impair.py <capture> <run.sqlite> <marks>` per condition. Each condition starts 10 s after its mark.
